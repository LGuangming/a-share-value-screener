# VPS Control Bridge V2.2 — offline maintenance and approved runtime switching

V2.1 was actually installed and its capabilities query succeeded. Inventory
issue #4 returned permission_denied despite traversal-only ACLs: the old
open_local used O_RDONLY on every ancestor, requiring read permission.
V2.2 uses Linux O_PATH + O_DIRECTORY + O_NOFOLLOW on ancestors and still
requires read access to the final requested directory/file. No widening of
ancestor ACLs or symlink following. Inventory now includes receipt counts
by year, still presence only (not completeness or data quality).

It uses the independent research worker (no network, 1 CPU, 1 GiB), and
never changes production archive or database. The required runtime must
contain the accepted BT03 modules (PR #44); BT05 is a distinct PR #46.
A unified runtime requires separate integration acceptance.

Create /etc/ashare-control/maintenance.json as root:ashare-control-research,
mode 0640. Paths below are examples, verify actual archive and evidence

      "python":"/opt/ashare-research-runtime/bin/python",

        {"stage":"market","year":2025,"month":1},

Local plan permits 1..180 batches, fixed completed-year market/security
month (2020–2025) or incremental committed market day (2026+). A matching

evidence is not synthesized. No remote parameters. Existing source archive
and evidence are read-only; grant ashare-research precise read/traverse
ACLs only on accepted input paths. No assumption the archive is present
on this host. Output and scratch live under
/var/lib/ashare-research-work/<dataset> (not the production/acceptance

Add bt03-maintain to locally authorized research-worker.json profiles

## Controlled research upgrade and rollback

Do not download a mutable Git branch, execute a remote shell or grant a
privileged self-updater. For version switching, first a local administrator
or separately trusted release installer prepares two immutable reviewed
runtime directories, baseline and candidate. Both must be from their
exact accepted revisions and CI-tested; local administrator reviews the
runtime environment/dependencies and binds its source/executable digest.
The bridge cannot install packages, fetch new releases as root, or approve
unreviewed code. A CI result alone is not proof of local file contents.

Create root-owned /etc/ashare-control/runtime-registry.json (0640,
root:ashare-control-research), with two entries of this shape:

    {
      "baseline":{
        "revision":"<actual 40 hex revision>",
        "python":"<root-owned immutable non-symlink python executable>",
        "backend":"<root-owned immutable backend tree>",
        "python_sha256":"<actual 64 hex sha256>",
        "backend_sha256":"<actual 64 hex tree digest>"
      },
      "candidate":{ "...":"same fields for separately accepted candidate" }
    }

Compute executable digest using sha256sum; backend digest using
    python3 /opt/ashare-control/runtime_slots.py digest /absolute/backend
The digest rejects symlinks, non-root ownership, group/world-writable paths
and oversized trees. Dependency/runtime immutability beyond executable is
a separate local approval condition. Do not use production working tree.

Opt in by adding use_approved_runtime:true to root-owned research.json and
maintenance.json. Preserve python/backend fields (selected verified slot
overrides these). Baseline is default. Add only root-approved wrappers
runtime-activate and runtime-rollback to research-worker.json and the bridge
async_profiles, routed research. They select only candidate or baseline,
verify digests before changing atomic selection, cannot introduce a third
release. Existing research run/maintenance dataset identity freezes
configuration; choose a new run/dataset identity after release change.
Rollback is runtime selection only, not rollback of output data or DB.
Never claim a failed candidate is deployed. Optional report alias
runtime-status (kind runtime) reads runtime-status.json in research work
with explicit ACL; it returns selected slot and revision only.

## Production upgrades

The existing production pipeline already has a separate release/publish
gate and VPS deploy mechanism. Reuse that mechanism, not this research
worker. A new privileged deploy or bridge self-update is NOT enabled by
this change. Keep destructive operations, production database changes,
container/socket access and root commands outside this bridge. A later
signed/independently approved installer can stage future releases; until
then root prepares immutable candidates and bridge upgrades locally.
No production merge/deploy, data deletion, live maintenance, collection
or remote version switching is claimed by this PR.
