# VPS control bridge v2 — A-Share operations and backtesting

Upgrade of the existing working private GitHub bridge. The issue title and
schema stay VPS CONTROL v1 / ashare-vps-control-v1 for backward compatibility.
The capabilities task returns bridge_version 2. No production deployment,
arbitrary shell, Docker socket, raw logs, file reads or credential access.
All returned report content is field-allowlisted and limited to 4 MiB input.
Inventory checks receipt presence, not actual data integrity or coverage.

## Upgrade the installed v1

Wait for CI of the exact accepted v2 commit and review the changes.
Use the existing separate /opt/ashare-control-source checkout, not the
production repo. Fetch the branch, checkout the exact accepted SHA, run:

    python3 -m unittest discover -s ops/vps-control -p 'test_*.py' -v
    bash ops/vps-control/upgrade-v2.sh

The script pauses the timer and refuses to interrupt an active task, backs
up installed source/config locally under /root (does not copy token), preserves
the private queue credentials and durable state, installs the fixed wrappers
and leaves the service paused. No new remote permission is enabled by the
upgrade itself. Review the config and explicitly start:

    systemctl start ashare-vps-control.service
    systemctl enable --now ashare-vps-control.timer

If an installation step fails, keep timer paused and review the backup.
Do not reset /var/lib/ashare-control to retry.

## Inventory and reports

Edit /etc/ashare-control/config.json locally. Keep existing repository,
repository_id, actor_ids and profiles exactly as configured. Add optional
inventory and reports objects. Example paths are NOT verified on the VPS:

    "inventory": {
      "market": "/opt/ashare/backtest/02_standardized/market",
      "security": "/opt/ashare/backtest/02_standardized/tradeability",
      "dividend": "/opt/ashare/backtest/evidence/dividend-v1",
      "reference": "/opt/ashare/backtest/evidence/reference-v1"
    },
    "reports": {
      "jan-preflight": {"kind":"preflight","file":"/var/lib/ashare-control-work/jan-v1/preflight.json"},
      "jan-signals": {"kind":"signals","file":"/var/lib/ashare-control-work/jan-v1/signals/summary.json"},
      "jan-portfolio": {"kind":"portfolio","file":"/var/lib/ashare-control-work/jan-v1/portfolio/summary.json"},
      "jan-walk": {"kind":"walk","file":"/var/lib/ashare-control-work/jan-v1/walk/summary.json"},
      "jan-progress": {"kind":"progress","file":"/var/lib/ashare-control-work/jan-v1/progress.json"},
      "containers": {"kind":"containers","file":"/var/lib/ashare-control-snapshots/docker.json"}
    }

If the real BT03 root is an acceptance subdirectory, use that exact root.
Missing/read-denied/invalid paths are reported separately, not as zero
coverage. Use selective filesystem read/traverse ACLs for the service
account on approved market/security/evidence roots. Never recursively chmod
the production tree or give the user Docker/sudo privileges. Symlinks
in directory and report paths are refused. Only locally chosen aliases
are exposed; remote requests cannot provide paths. Report contents are not
proof of independent verification.

Issue bodies (exact JSON, no Markdown fences; title VPS CONTROL v1):

    {"schema":"ashare-vps-control-v1","task":"capabilities"}
    {"schema":"ashare-vps-control-v1","task":"data_inventory"}
    {"schema":"ashare-vps-control-v1","task":"task_status"}
    {"schema":"ashare-vps-control-v1","task":"backtest_status","report":"jan-preflight"}
    {"schema":"ashare-vps-control-v1","task":"task_logs","report":"jan-progress"}
    {"schema":"ashare-vps-control-v1","task":"docker_status","report":"containers"}
    {"schema":"ashare-vps-control-v1","task":"deployment_status","report":"deployment"}

Task logs means structured progress only; no arbitrary log lines. Deployment
status requires a locally produced, approved JSON snapshot of kind deployment
with status LOCAL_DEPLOYMENT_SNAPSHOT_V1, state unknown/healthy/unhealthy/
pending, optional revision (40 hex chars) and captured_unix. No producer
or deploy command is supplied for this optional report.

For Docker, a local administrator may produce an allowlisted snapshot:

    install -d -o root -g root -m 0755 /var/lib/ashare-control-snapshots
    # locally create /etc/ashare-control/docker-map.json using real names:
    # {"web":"actual-web-container","worker":"actual-worker-container"}
    python3 /opt/ashare-control/docker_snapshot.py --mapping /etc/ashare-control/docker-map.json

The bridge gets only aliased state + snapshot time, not real container names,
logs, Docker access or environment. Snapshot may be stale until refreshed by
the local administrator; no root timer is installed automatically.

## Offline BT04/BT05 execution

Required first: accepted BT03 data, actual reviewed calendar/actions/index
and fees, and accepted BT05 code/runtime. PR #44 and #46 are independent of
this bridge. Do not use the production code tree or a mutable unreviewed
checkout. Python 3.11+ with required DuckDB dependencies in a root-owned,
non-symlink trusted executable (a root-owned venv created with --copies is
one option). Root must review the entire runtime/backend tree, not just
its root directory. No production credentials supplied to subprocess.

Create /etc/ashare-control/research.json (root:ashare-control, 0640).
Example only, replace paths using verified local inputs:

    {
      "python":"/opt/ashare-research-runtime/bin/python",
      "backend":"/opt/ashare-research-source/backend",
      "market":"/opt/ashare/backtest/02_standardized/market",
      "security":"/opt/ashare/backtest/02_standardized/tradeability",
      "dividend":"/opt/ashare/backtest/evidence/dividend-v1",
      "calendar":"/opt/ashare/backtest/evidence/reference-reviewed-v1/calendar.json",
      "benchmark":"/opt/ashare/backtest/evidence/reference-reviewed-v1/benchmark-000300.SH.json",
      "actions":"/opt/ashare/backtest/evidence/actions-v1.json",
      "fees":"/opt/ashare/backtest/evidence/fees-v1.json",
      "warmup":"2024-07-01",
      "start":"2025-01-01",
      "end":"2025-01-31",
      "run_name":"jan-v1",
      "shards":2,
      "execution_config":null,
      "walk_plan":null
    }

The local run identity freezes the config and hashes of evidence files.
Choose a new run_name for a changed config/evidence; do not overwrite
receipts. Results and scratch live under /var/lib/ashare-control-work,
separate from original source, production and existing task state. Runtime
code is expected to remain pinned and immutable to the service. The BT03/
BT04/BT05 receipt gates still apply. Local preflight must pass before
signals, a signal summary is required before portfolio, and portfolio
summary is required before walk-forward. A passing short-window preflight
does not certify a larger walk plan; the walk runner verifies its own inputs.

After root has reviewed all paths, inputs and scripts, add to config.json
profiles (merge with existing, not overwrite):

    "profiles": {
      "bt05-preflight": {"script":"/opt/ashare-control/profiles/bt05-preflight","timeout_seconds":1800},
      "bt05-signals": {"script":"/opt/ashare-control/profiles/bt05-signals","timeout_seconds":7200},
      "bt05-portfolio": {"script":"/opt/ashare-control/profiles/bt05-portfolio","timeout_seconds":7200},
      "bt05-walk": {"script":"/opt/ashare-control/profiles/bt05-walk","timeout_seconds":7200}
    }

Enable only those profiles the operator actually approves. Remote requests
have no date, path, flag or command arguments, e.g.:

    {"schema":"ashare-vps-control-v1","task":"run_profile","profile":"bt05-preflight"}

One task at a time. While a long profile runs, this v2 synchronous service
cannot answer another status request. A request expires after 15 minutes,
so do not queue additional requests during a long task. Profile timeout
kills the process group; a prior progress snapshot may remain running,
so the issue's timeout result is authoritative for that task. Local logs
capped at 1 MiB per stage, retained locally, not remotely transmitted.
Successful exit does not establish formal backtest readiness.

## Deferred/disabled

Online dividend/index collection needs a separate credential-isolated
worker and locally approved account-wide request budget; not enabled by
this offline runner. The bridge must not be given Tushare credentials,
root/Docker group, arbitrary shell, production restart or deploy powers.
No data permissions or runtime installations assumed. Actual live upgrade
and acceptance must be performed after CI; no actual backtest result is
claimed. Existing v1 status task remains compatible.
